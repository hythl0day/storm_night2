# 性能与交互改进计划：篇幅约束 + 流式调用 + 统一控制台

> 起因：M4 实测中单次 API 调用耗时 200s（`game/012345/host_log.jsonl` 唯一记录：奇米·开局准备，200.57s / total_tokens 7766），
> 第 1 天约 36-44 次串行调用 → 全天预计 2-2.5 小时，无法接受。本文档是改进计划，**尚未实施**。
> 待拍板项汇总在 §6。

## 1. 诊断结论（已确认）

| 因素 | 性质 | 说明 |
| ---- | ---- | ---- |
| 输出篇幅失控 | 主因 | 四通道 JSON 中 inner 动辄上千 token；`max_tokens = 131072` 等于不设防 |
| 全串行调用 | 设计使然，基本不改 | 发言/交换/选房/夜晚邀请的顺序依赖是游戏机制本身（用户判断正确，见 §4） |
| 非流式黑盒等待 | 代码可改 | 200s 无任何反馈；120s 读超时靠中转站持续吐字节才侥幸不触发 |
| 超时/重试粗放 | 代码可改 | 任何异常都无差别重试 2 次；一次卡死可白烧 6 分钟 |

ping/smoke 感觉快的原因：只让模型回 1 个字，且 smoke 用线程池八席并发——与对局负载没有可比性。

## 2. 输出篇幅控制：prompt 约束为主，max_tokens 只作安全网

### 2.1 关于"max_tokens 会不会打断模型思考"

会，而且是双杀：`max_tokens` 是**硬截断**，切在 JSON 中间 → 解析失败 → 重试重生成 → 比原来更慢。
因此它**不能当主要约束手段**。方案调整为：

- **主手段：prompt 篇幅纪律**（写进 `prompt/game_system.md`，见 2.2），让模型自觉写短；
- **max_tokens 只作失控安全网**：131072 → **16384**。正常回复 1-2K token，永远触不到；
  只在模型失控死循环输出时兜底。16384 也给推理模型的隐藏思考留足余量，不会切断思考链；
- 解析响应时检查 `finish_reason == "length"`：一旦出现说明安全网被触发，记 host_log 并按解析失败处理（重试 1 次），用于发现"安全网设低了"的情况。

### 2.2 prompt 篇幅纪律（拟加入 game_system.md 的草稿）

```markdown
## 输出篇幅纪律（必须遵守）

- speech：像日常说话一样简短，单次不超过 150 字。
  仅当进行复杂逻辑陈述（完整的指控链/不在场证明推演）时可放宽到 400 字。
- inner：写**摘要**，不写完整推理过程。不超过 200 字；
  仅在面对重大抉择（谋杀/关键指控前）时可展开到 500 字。
- notes：结构化要点（每行一条），总计不超过 300 字。写给未来的自己，只记结论和待办。
- actions：只填合法动作 JSON，不要解释。
```

预期效果：单次输出从 1-2K token 压到 400-700 token，单次调用 200s → 60-90s。

**代价（需拍板）**：inner 内心独白是剪辑素材，缩短 = 素材变少。2.2 的"重大抉择可展开"是折中——
日常注水压掉，关键戏保留。字数基线（150/200/300）可调。

## 3. providers.py 流式改造

`chat()` 增加流式模式（`"stream": true`，SSE 逐块读取），并提供 `on_token` 回调：

1. **体验**：控制台可实时滚动显示模型输出，200s 黑盒变成可见进度。
2. **健壮性——超时分层**：
   - 连接超时 10s；
   - **停滞看门狗**：90s 无任何新字节 → 判定挂起，主动断开（取代现在 120s 整体读超时）；
   - 总墙钟上限 600s。
3. **重试精细化**：HTTP 4xx 不重试（401/404 重试无意义）；429/5xx/网络错误指数退避，429 尊重 Retry-After；停滞断开可重试。
4. **协议兼容**：OpenAI 与 Anthropic 的 SSE 格式分别解析；某上游不支持流式时，该次调用自动回退非流式并记日志。
5. **usage 统计**：流式下部分上游不返回 usage，用字符数估算 token 数（中文 ≈ 字/1.5）供速度显示，真实 usage 有则用。
6. 每次调用新建 `httpx.Client` 的开销（TLS 握手 ~1s）顺手改为模块级复用——相对 200s 是零头，但免费。

## 4. 并发：维持串行，不做

重新核对过各环节的信息依赖，用户"能并行的不多"的判断成立：

- 发言/交换/选房：顺序即机制，不可动；
- 晚间休息：看似"互相不可见"，但**顺序靠后者能在简报里看到靠前者的留宿邀请**（`run_night` 的 pending_invite），有真实顺序依赖，不可并发；
- 开局准备（密道/窃听器声明）理论上独立，但最多省 1 次调用时长，收益不抵复杂度，**不做**；
- 将来若加"每阶段剪辑素材总结/recap"这类**纯侧路**调用（不进游戏状态），那才是并发/后台执行的正确位置。

提速全部指望 §2（篇幅）+ §3（健壮性），主循环保持严格串行，公平性设计零改动。

## 5. 交互层：console 驾驶舱 + view 查看器（分层并存）

针对 M4.5 原定 `view.py`（只读查看器）与本次新增控制台的关系，按三层组织，逻辑零重复：

### 5.1 模块分工：console 不取代 view.py

- `viewer.py`（视图层，M4.5 的本体）：纯函数读 `game/<id>/` 存档，渲染 status/log/peek 文本。
  与跑局完全解耦——跑完的局、别的机器上跑的局都能看；
- `view.py`（薄壳，保留 M4.5 原定形态）：argparse 子命令 `status`/`log`/`peek`/`follow`（轮询刷新）
  包装 viewer 函数。用途：复盘已结束的对局、M6 批量跑局时旁路查看；
- `console.py`（驾驶舱，本计划新增）：进程内驱动 orchestrator，流式渲染 + 随时交互。
  其 `status`/`log`/`peek` 命令**直接调 viewer 函数**（同一份代码）；`follow` 用流式钩子原生实现，取代轮询。

新入口：`python -m src.console --game game/012345 [--resume]`。

### 5.2 与 orchestrator 的关系：不重复造轮子

console 是**新增的交互壳模块**，游戏规则与流程代码仍只在 orchestrator.py 里一份：

- `orchestrator.py`（保留）：游戏运行核心——Orchestrator 类（简报生成、call_ai、动作裁决、阶段推进）。
  其现有 `main()` 保留为**无头模式**，供 M6 批量跑局用（批量场景不需要交互界面）；
- `console.py`（新增）：只做三件事——订阅事件渲染 UI、转发用户命令、控制暂停/恢复，不含任何游戏规则代码。

为此需要一次小重构（不改任何游戏行为）：

1. 把 `main()` 里的阶段推进循环（while True + stage 分支）提炼为 `Orchestrator.run_day()`，
   无头 `main()` 与 console 共用同一份推进逻辑，避免两处各写一份流程；
2. 在 `call_ai` / `advance` 上加观察者回调钩子（`on_call_start(seat, stage)` / `on_token(text)` /
   `on_call_end(result)` / `on_stage(title)`）。console 订阅这些钩子做渲染；
   无头模式不订阅（或挂一个简单打印器），行为与现在完全一致。

### 5.3 架构

- **工作线程**：现有 `Orchestrator` 主循环原样跑，不改游戏逻辑；
- **UI 线程**：渲染底部瞬时状态/输入行 + 流式输出区；
- **stdin 读取线程**：Windows 下 stdin 无法用 selector，用守护线程阻塞读 `input()`，命令入队；
- **不引入新依赖**（维持"只有 httpx"的硬性约定）：spinner 和顶栏用 ANSI 转义序列手写。

### 5.4 界面形态（两轮实测后的定稿）

```
── 杰米娜 · 公共发言 ──────────────────   ← 调用开始即打印（青色标题）
（思考内容灰色滚动，按"行"批量吐出）
杰米娜：（发言，亮白加粗）                 ← 解析完成后的卡片
（内心）……（灰色）
→ {"type": "choose_room", "room": "书房"}（黄色）
  (12.3s · 500 tok)
────────────────────────────────────────   ┐
> 输入缓冲▌                                 ├ 底部固定三行块
第1天·公共发言 | 杰米娜·公共发言 ⠋ 47s·312字  ┘
```

- 输出走正常终端滚动流，**滚轮可回看全部历史**
  （首版固定顶栏 + 滚动区会吞历史且宽度适配差；二版"状态+输入一体行"因变长抖动被拆成两行——
  输入行带固定光标 ▌，状态行独立置于其下）；
- 提示块只在输出处于**行首**时存在：思考流缓冲到最后一个换行符才吐出，
  因此流式期间输入行/状态行始终可见、打字即时回显；
- 渲染分工：思考灰色滚动；JSON 不刷屏，解析完成后渲染人读卡片
  （发言亮白 / 内心灰色 / 行动黄色 / 调用间标题分隔线）。

### 5.5 命令集（首版）

| 命令 | 作用 |
| ---- | ---- |
| `status` | 天数/阶段/存活名单/位置/已发生的公开事件计数 |
| `log [n]` | 最近 n 条 public/log.md |
| `peek <seat>` | 查看该席私密卡 + notes |
| `inner <seat>` | 查看该席内心独白存档 |
| `follow <seat>` | 锁定实时跟随某席的输出流；默认跟随当前正在调用的席位 |
| `pause` / `resume` | 在**阶段边界**暂停/继续（检查点，不打断进行中的单次调用） |
| `save` / `quit` | 立即落盘 state / 落盘后退出（当前阶段状态已可 --resume） |

### 5.6 与后续里程碑的关系

- **M7 人机模式**：console 即载体——真人席位 = 该席位的 `call_ai` 替换为控制台输入（briefing 展示 +
  等待用户提交 JSON）。本次把 `call_ai` 的输入抽象留好，M7 不再返工；
- **M8 看海模式**：viewer 层轮询全部私密目录，或 console 钩子广播全席位流，届时二选一。

## 6. 实施步骤与验收

按序执行，每步可独立验收：

1. **benchmark 脚本**（建议先做，半小时出数据）：`tools/bench.py`，对每个席位各发"短 prompt+短输出"
   与"实战 prompt 长度+要求 500 字输出"两种请求，流式记录 TTFT/tok/s/总时长，输出表格。
   用途：确认 200s 里模型生成 vs 中转站开销的构成，验证篇幅约束的预期收益；数据也用于 §6-待拍板的字数基线。
2. **篇幅约束**：改 `prompt/game_system.md` + `players.toml` 的 max_tokens=16384 + finish_reason 检测。
   验收：重跑 seed 12345 第 1 天，抽查 outbox 超标率 <20%，host_log 中位延迟 ≤90s。
3. **流式改造**：providers.py 按 §3。
   验收：人为拔网/限速场景下，停滞 90s 内必报错且总重试耗时可控；正常调用 token 流可见。
4. **视图层 + 控制台**：viewer.py / view.py（M4.5 薄壳）+ console.py 按 §5。
   验收：view.py 四个只读子命令对已落盘对局可用；console 调用进行中敲 `status`/`log` 即时响应；`pause` 后 state.json 完整可 `--resume`；全程无 ANSI 渲染错乱（GBK 控制台已 reconfigure UTF-8 的前提下）。

总验收：seed 12345 第 1 天全天无干预跑完，**墙钟 ≤ 45 分钟**（现为估 2-2.5h），落盘齐全，phase 进第 2 天。
